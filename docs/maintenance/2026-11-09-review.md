## 已修正

1. **按鈕回覆過晚**：原本先查成員、資料庫，再修改 Discord 身分組，最後才回覆。Discord 要求互動於 3 秒內確認；現在辨識 `rr:` 按鈕後立即送出私人 deferred reply，再更新結果。[Discord.js 官方互動文件](https://github.com/discordjs/guide/blob/main/guide/interactive-components/interactions.md)
2. **按鈕錯誤沒有統一回覆**：原本只有音樂按鈕位於路由的 try/catch。身分組、抽獎、投票按鈕拋錯時會跳過錯誤回覆，事件入口也沒有處理 rejected promise。現在所有按鈕共用既有錯誤回覆，入口另記錄無法完成回覆的錯誤。
3. **權限與身分組層級缺少執行時檢查**：現在在修改前確認 Manage Roles、目標身分組存在、可編輯且不是 @everyone；失敗時提示管理員檢查整合管理身分組與排序。Dashboard 原有儲存驗證無法防止儲存後的 Discord 權限變更。[Discord 官方權限文件](https://github.com/discord/discord-api-docs/blob/main/developers/topics/permissions.mdx)
4. **單選模式忽略移除失敗**：原本吞掉移除其他選項的錯誤，仍新增目標並回報成功。現在只處理成員持有的其他面板身分組，先驗證可編輯性，移除失敗即停止；取消目前選項時不再清除其他選項。
5. **成員快取與伺服器邊界**：按鈕強制取得最新成員資料；共用角色處理確認選項與面板都屬於目前伺服器。

修改範圍只有 Bot 的身分組共用處理、互動路由、事件入口及既有測試檔；不需變更資料庫、Dashboard API、按鈕 ID 或重新註冊 slash commands。共用身分組檢查也適用 Emoji reaction 呼叫路徑。

### P1：其他互動仍有逾時風險

- `apps/bot/src/lib/polls/polls.ts` 的 `handlePollButton` 在資料庫讀寫與更新投票訊息後才回覆。
- `apps/bot/src/lib/giveaways/giveaways.ts` 的 `handleGiveawayButton` 在資料庫與成員查詢後才回覆。
- `apps/bot/src/lib/tickets/tickets.ts` 的開單在查詢設定與未關閉數量後才 defer；領單也在成員、設定與資料庫操作後才回覆。

這些路徑已受益於本次統一錯誤回覆，但仍應各自把確認互動提前，並測試所有提早返回路徑。本次未改動它們的回覆語意。

### P2：錯誤日誌可讀性不足

`apps/bot/src/lib/logger.ts` 直接 JSON.stringify metadata。原生 Error 的 message / stack 不可列舉，經常被輸出為 `{}`，不利於區分 Missing Permissions、Unknown Interaction 與資料庫錯誤。後續應只序列化必要錯誤欄位，並保留敏感值遮蔽的邊界。
